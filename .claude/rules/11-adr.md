# 11 决策流程（ADR）

> 目标：关键决策写下来，评审过再改代码。思想见 rules/00 P8。

## 哪些改动必须走 ADR

1. 技术栈主框架（如后端换框架、引入新重型组件）
2. API 统一错误体 / 响应格式
3. 数据模型主表（新增/变更表或关键字段）
4. 安全护栏（DDL 拦截策略、权限模型）
5. 原则 P1-P9 本身
6. 架构方案"待探测确认"项定案（探测结果填实时）

> 普通规则调整、常规 Bug 修复、新增一个 API 端点（契约内）**不用** ADR。

## ADR 模板（`docs/ADR/ADR-XXX-<slug>.md`）

```markdown
# ADR-XXX: <决策标题>

- 状态: 提议 / 已接受 / 已废弃
- 日期: YYYY-MM-DD
- 背景: 为什么要做这个决策（问题、约束、触发场景）
- 决策: 最终选择（明确、一句话可执行）
- 备选方案: 至少列出 1~2 个候选 + 否决理由
- 影响: 对现有代码/端口/数据模型/内存的影响
- 验证: 如何证明决策正确（验收点）
```

## 流程

1. 写 ADR（提议状态）→ 2. 与用户/主会话评审 → 3. 更新 `docs/架构设计方案.md` → 4. 按新决策改代码 → 5. ADR 标记"已接受"

## 本地小步原则

- 个人项目不搞重型评审会：ADR 文档 + 用户确认即算评审通过
- 决策可逆则用"最小改动验证"（先改代码验证，再补 ADR）；不可逆/影响广则先 ADR 后代码
